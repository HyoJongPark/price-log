# 무엇을 테스트할까

구현자와 리뷰어는 먼저 묻는다. **어떤 결함이 생기면 누가 무엇을 잘못 보거나 잃는가?** 그 결함을 드러낼 시작 상태, 행동, 관찰 가능한 결과를 고른다. 같은 결과를 보장하는 리팩터링 후에도 단언이 유효해야 한다.

## 어떤 차이가 실패로 드러나야 하는가

- 한 번의 입력으로 설명할 수 없는 동작은 그 전의 상태부터 만든다. 처음 방문했을 때와 이미 방문한 뒤 다시 열었을 때처럼, 같은 입력이라도 결과를 달리하는 이력을 고른다.
- 실패 중 일부만 저장됐거나, 같은 요청을 다시 보냈거나, 둘이 동시에 수정했을 때 누가 피해를 보는지 살핀다. 계정이 있는 동작은 다른 사람의 상태까지 바뀌는지도 고려한다. 변경과 관련 있는 경로를 선별한다.
- 기대값은 제품 결정이나 외부 계약에서 가져온다. 구현과 같은 수식·분기문을 테스트에 복제하면 양쪽이 같은 오류를 낼 수 있다. mock 호출 횟수나 순서는 호출 자체가 사용자에게 약속한 효과일 때 단언한다.

## 범위별 파일 배치와 이름

**한 테스트 클래스는 한 가지 실행 범위를 갖는다.** 같은 환경에서 확인하는 성공·실패·경계값은 함께 둔다. 같은 대상을 검증하더라도 한쪽이 실제 DB나 Spring 컨텍스트를 필요로 하면 파일을 나눈다. 검증할 동작이 있는 범위에만 파일을 만든다.

| 범위 | 위치와 이름 | 무엇을 확인하는가 |
| --- | --- | --- |
| 단위 | Java는 `src/test/java`에서 운영 패키지에 대응하는 `<대상>Test`. 프런트엔드는 대상 옆의 `<대상>.test.ts(x)` | 하나의 정책·컴포넌트를 격리해 입력에 따른 결과를 확인한다. 예를 들어 `SteamAppListClientTest`는 클라이언트를 직접 생성하고 HTTP 응답을 대체한다. |
| 통합 | Java는 대상 패키지의 `<대상 또는 기능>IntegrationTest` | 실제로 연결해야 드러나는 계약을 확인한다. Spring 조립, SQL 제약, 서비스 호출 후 커밋·롤백 결과가 여기에 해당한다. |
| 인수 | 독립된 서버 시나리오가 여러 기능을 거치면 테스트 루트 패키지의 `acceptance/<사용자행동>AcceptanceTest` | 공개 진입점을 통해 사용자가 기대한 결과를 확인한다. 기존 단위·통합 테스트로 인수 조건을 충분히 검증하면 그 테스트를 사용한다. |
| 브라우저 E2E | 프로젝트 루트의 `e2e/<사용자여정>.spec.ts` | 브라우저에서 제품을 조작해 프런트·백엔드·테스트 DB를 거친 결과까지 확인한다. 외부 공급자 응답은 고정할 수 있다. |

외부 서비스의 실서버 확인은 인증 또는 명세 변경을 점검할 때 소량으로 수동 수행한다. 일반 회귀 테스트는 로컬에서 재현할 수 있는 입력과 격리된 환경을 사용한다.

## Java 테스트 작성

테스트 본문에 `// given`, `// when`, `// then`을 두고 준비한 상태, 실제 호출, 관찰한 결과를 분리한다. 실패 시나리오는 `when`에서 예외를 포착하고 `then`에서 기대한 실패 이유를 단언한다. 재시도처럼 행동 순서 자체가 계약이면 중간 결과도 확보한다.

한 테스트 클래스에서 기능별 시나리오를 다룰 때는 `@Nested`와 한국어 `@DisplayName`으로 묶는다. 예를 들어 Web API 테스트는 카탈로그와 동접 조회를 나누고, 한국 상점 테스트는 할인 가격과 명시적 0원을 같은 가격 조회 계약의 사례로 묶는다. 같은 계약에서 입력만 달라지면 이름 있는 파라미터 행으로 표현한다. 단일 연결 확인처럼 사례 하나로 끝나는 테스트는 바로 작성한다.

서비스 테스트는 작업의 결과·실패 격리에, 클라이언트 테스트는 HTTP 요청과 응답 해석에, JPA 매핑·중복·잠금 검증은 PostgreSQL에 초점을 맞춘다. 원천을 분리할 때는 인증 헤더가 필요한 요청에만 붙는지와 누락된 응답이 유효한 0으로 저장될 가능성을 확인한다. 관측 순서와 날짜 경계는 고정한 관측 시각을 입력해 검증한다. 트랜잭션 경합을 검사할 때는 각 호출이 독립적으로 커밋될 수 있게 구성한다.

## 어느 수준에서 잡히는가

| 깨질 수 있는 약속 | 확인 방법 |
| --- | --- |
| 값 계산, 정책, 상태 전이 | 대표 입력과 전후 결과를 작은 단위 테스트에서 대조한다. 시간·순서가 중요하면 고정된 시각과 순서를 준다. |
| HTTP 요청·응답 계약 | 상태 코드, 응답 본문, 권한에 따라 실제로 노출되는 값을 웹 계층에서 확인한다. 같은 정책의 상세 조건은 단위 테스트에 둔다. 응답 의미가 바뀌면 React 호출부가 빈 결과와 요청 실패를 의도대로 구분하는지도 확인한다. |
| SQL 정렬, 제약, 트랜잭션, 계정 간 데이터 격리 | Testcontainers의 PostgreSQL 17에서 실제 쿼리나 애플리케이션의 저장 진입점을 호출하고 최종 상태를 읽는다. 로컬 DB를 재생성할 수 있는 개발 단계에는 현재 스키마의 저장 동작을 검증한다. 기존 데이터를 반드시 보존해야 하는 시점부터, 그 데이터에 영향을 주는 변경에 마이그레이션 테스트를 추가한다. |
| 외부 서비스와 주고받는 값 | 테스트 대역으로 요청과 응답 해석, 실패 처리를 확인한다. 실제 서비스 연결을 확인했다면 대상과 결과를 별도로 밝힌다. |
| 포커스 이동, 터치, 화면 전환, 배치 | 실행한 화면에서 변경에 영향받는 입력 장치와 뷰포트로 조작한다. 연속 조작과 완료 후 상태를 확인한다. 스크린샷은 배치를 대조할 때 쓴다. |

새 동작이나 버그를 잡아낼 기존 테스트가 없으면 그 결함을 드러내는 테스트를 작성한다. 기존 테스트가 이미 같은 실패를 잡으면 해당 사례를 실행한다. 단순 접근자나 프레임워크 기본 동작은 독립 테스트를 생략할 수 있다. DTO에 공개할 필드, 금액 단위, 날짜 형식처럼 변환 결과 자체가 계약이면 호출자가 받는 값을 검증한다.

테스트만 손볼 때는 먼저 원래 계약과 테스트가 관찰하던 결과를 확인한다. 리팩터링 후에도 같은 결함에서 실패해야 한다. 기대값을 바꿨다면 근거가 된 요구사항 변경을 짚고, 수정한 테스트를 실행한다.

리뷰에서는 **어떤 잘못된 구현도 이 테스트를 통과할 수 있는가?**를 묻는다. 예컨대 첫 항목과 두 번째 항목의 값이 같다면 잘못된 항목을 갱신해도 테스트가 통과할 수 있다. 차이가 드러나는 데이터나 관찰 지점으로 고친다. 최종 보고에는 실제로 확인한 동작, 실행하지 못한 검사와 그 이유를 적는다.

## 검증 실행

작성 중에는 변경을 검증하는 가장 작은 테스트를 실행한다. SQL을 바꾸면 관련 DB 통합 테스트를 바로 실행한다. **커밋 직전에는 재현 가능한 자동 테스트 전체를 실행한다.** 현재는 `backend/`에서 `./gradlew build`, `frontend/`에서 `npm run lint`와 `npm run build`를 실행한다. 프런트엔드의 현재 검증 범위는 정적 검사·타입 검사·번들 생성이다.

백엔드 명령은 `backend/`에서 실행한다. DB 통합 테스트는 Docker 엔진을 사용하며, Testcontainers가 별도 PostgreSQL 17을 띄운다. 개발용 Compose DB는 꺼 두어도 된다.

| 명령 | 확인하는 것 |
| --- | --- |
| `./gradlew checkstyleMain checkstyleTest checkstyleConventions` | 운영·테스트 Java 코드의 정적 규칙과 서식 |
| `./gradlew test --tests '*SteamAppListClientTest*'` | Steam 목록 클라이언트의 단위 테스트와 중첩 시나리오 |
| `./gradlew test --tests '*IntegrationTest'` | DB 등 실제 연결을 검증하는 통합 테스트 |
| `./gradlew test` | JUnit 테스트와 격리 DB 쓰기·조회 |
| `./gradlew build` | 정적 검사·테스트를 포함한 전체 빌드와 JAR 생성 |

자동 테스트는 테스트용 키나 클라이언트 대역을 사용한다.

프런트엔드 명령은 `frontend/`에서 `npm ci` 후 실행한다.

| 명령 | 확인하는 것 |
| --- | --- |
| `npm run lint` | Biome 린트·서식 검사. 서식을 적용할 때는 `npm run format` |
| `npm run typecheck` | TypeScript 타입 |
| `npm run build` | 타입 검사와 배포용 번들 생성 |

### 정적 검사 기준

Java 운영 코드와 테스트 코드는 [Google Java Style Guide](https://google.github.io/styleguide/javaguide.html)를 따른다. 프로젝트 규칙으로 블록마다 공백 4칸을 들여쓰고, 줄 길이는 원칙적으로 100자로 제한한다. [Gradle 설정](../backend/build.gradle)에서 Checkstyle에 포함된 `google_checks.xml`을 사용하며, 경고 한 건도 빌드 실패로 처리한다. 프로젝트 Checkstyle 규칙은 명시적 지역 변수 타입, 엔티티 필드 간격, 영속 시각 타입, 컨트롤러·서비스·저장소 이름의 접미사를 검사한다. 책임 배치와 문단 구분은 [백엔드 개발과 리뷰](../backend/AGENTS.md)를 따른다.

프런트엔드는 [Biome 설정](../frontend/biome.json)에 기본 권장 규칙과 [React 권장 규칙](https://biomejs.dev/linter/domains/#react)을 명시한다. 조건부 Hook 호출 같은 오류와 서식을 함께 검사하고 경고도 실패로 처리한다. 서식은 공백 2칸, JavaScript 작은따옴표, 필요한 경우에만 세미콜론을 사용한다.
