# 변경을 커밋하기

## 범위와 단위

1. 현재 브랜치와 `git status --short --branch`, `git diff --cached`, `git diff`, 새 파일을 확인한다. “스테이징한 것만”이면 현재 인덱스가 범위다. 그 외에는 사용자 요청과 실제 변경을 대조한다.
2. 독립적으로 설명하고 검증할 수 있는 변경 이유마다 한 커밋을 만든다. 동작을 바꾼 코드와 그 회귀 테스트·필수 설정은 함께 둔다. 여러 커밋이 필요하면 각 중간 상태가 동작하도록 의존 순서를 잡는다.
3. 요청한 경로와 필요한 hunk만 stage한다. 같은 파일에 부분 staging이 있거나 범위 밖 변경이 이미 stage돼 있으면 기존 선택을 보존한다. 인덱스를 그대로 커밋하면 다른 변경까지 포함되는 경우, 범위를 확실히 격리할 수 있을 때만 진행하고 모호하면 어떤 변경을 포함할지 묻는다.

## 실행 전 검사

- 최종 `git diff --cached --check`와 staged diff를 읽어 의도한 변경·테스트만 포함됐는지 확인한다. 비밀값, 로컬 설정, 빌드 결과, 실험 파일이 끼어 있으면 제외 범위를 확인한다.
- 커밋 직전에는 [테스트 문서의 전체 검증 절차](../../../docs/testing.md#검증-실행)를 실행한다. 문서 변경은 내용과 링크도 확인한다. 작업 트리에 다음 커밋의 코드가 섞여 있으면 별도 공간에서 인덱스의 내용만으로 검증한다. 필수 검사 실패는 원인을 바로잡은 뒤 다시 실행한다.

## 메시지와 결과

- 제목은 `type: 변경 대상 + 수행한 작업`으로 쓴다. diff에서 무엇을 구현·추가·수정·제거했는지 짚는다. 최근 관련 제목은 `git log -12 --format='%h %s'`로 확인해 제품 용어를 맞춘다. scope는 구분에 도움이 될 때 쓴다.
- 예를 들어 새 스케줄러를 만들었으면 `feat: Steam 카탈로그와 게임 가격 수집을 위한 스케줄러 구현`으로 쓴다. 수집 주기·배치 크기 같은 실행 세부사항은 본문에 둔다. 기존 스케줄러의 주기 자체를 바꾼 작업이면 `fix: 게임 가격 수집 주기를 12시간으로 수정`처럼 바뀐 설정을 제목에 명시한다.
- 기능은 `feat`, 버그 수정은 `fix`, 동작을 보존하는 구조 변경은 `refactor`를 쓴다. 그 밖에는 주된 목적에 따라 `test`, `docs`, `style`, `build`, `ci`, `chore`, `perf`, `revert`를 고른다. 예를 들어 `docs: 로컬 검증 명령 정리`처럼 달라진 점을 제목에 드러낸다.
- 제목은 작업 하나를 한 줄로 요약하고 마침표를 생략한다. 함께 수행한 세부 작업이나 설명할 결정이 있으면 제목 아래 한 줄을 비우고 본문(description)에 한국어 불릿으로 적는다. 각 불릿에는 실제로 바꾼 내용과 필요한 경우 그 이유를 담는다. 제목만으로 변경이 충분히 드러나는 단순 작업은 본문을 생략할 수 있다. Git 작성자 설정을 유지하고 AI 작성자 트레일러는 넣지 않는다.
- 커밋 요청이면 검증한 인덱스로 일반 커밋한 뒤 생성한 해시·제목, 검사 결과, 남은 변경을 확인해 알린다. amend나 이력 재작성은 그 동작을 명시적으로 요청받았을 때만 수행한다.
