# 개발 워크플로우

## 요청을 코드에 연결하기

1. `git status --short --branch`에서 기존 변경을 확인한다. Graft로 요청이 닿는 진입점을 찾는다. 제품 화면이면 [제품 가이드](../../../docs/product.md)에서 해당 행의 PoC 코드, 테스트, 캡처를 찾아 사용자 행동을 대조한다.
2. 누가 무엇을 하면 무엇이 보여야 하는지, 이번 변경 뒤에도 어떤 행동을 유지해야 하는지 정한다. 작업에 쓰는 짧은 설명이면 충분하다. 코드·PoC로 확인할 수 없는 제품 결정이 결과를 바꾸는 경우만 사용자에게 묻는다.

Java 작업은 구현 전과 로컬 diff 리뷰 때 [백엔드 개발과 리뷰](../../../backend/AGENTS.md)를 적용한다. 데이터의 소유 패키지, 원천별 클라이언트와 트랜잭션 경계, 필드·문단 구분을 확인하고 변경 범위에 맞는 린트와 테스트를 실행한다.

## 작업을 나누고 재개하기

- 하나의 결과로 검증할 수 있는 요청은 바로 구현한다. 독립적으로 완료를 확인할 결과가 여럿이거나 여러 세션에 걸칠 때만 작업을 나눈다. 사용자에게 보이는 동작이나 호출자가 사용할 계약을 단위로 잡고, 앞 단위가 제공해야 할 결과와 각 단위의 완료 조건을 짧게 적는다.
- 이런 작업은 현재 체크아웃의 `docs/private/<작업명>/work.md` 한 파일에 원래 요청·합의한 범위, 브랜치(또는 HEAD), 단위별 순서·상태·완료 조건을 남긴다. 첫 단위부터 아래 구현·검증·리뷰 절차를 적용한다. 단위가 끝나거나 중단될 때 관련 파일·테스트, 실행한 명령과 결과, 남은 문제와 다음 행동을 갱신한다.
- 현재 단위의 검증·리뷰 결과가 완료 조건에 맞으면 기록을 갱신하고 요청 범위 안의 다음 단위로 이어간다. 검증이 막히면 원인과 미확인 조건을 남기고 의존하는 단위는 보류한다. 현재 요청 범위 안에서 진행할 수 있는 독립 작업은 계속한다. 마지막에는 전체 요청을 다시 대조하고 단위 간 연결도 검증한 뒤 기록에 완료를 표시한다.
- 새 세션에서 이어갈 때는 `docs/private/`에서 요청과 맞는 기록을 찾아 브랜치·현재 파일·커밋 및 미커밋 diff와 대조한다. 완료로 적힌 동작이 사라졌거나 관련 코드가 바뀌었으면 해당 단위를 다시 열고 영향받은 검사를 실행한다. 기록이 없으면 요청과 실제 코드·테스트로 진행 지점을 복원한다. 복수의 작업 중 대상을 식별할 수 없을 때만 사용자에게 묻는다.

## 현재 단위 구현과 검증

1. 메인 에이전트가 구현과 검증을 맡는다. 기능 추가·동작 변경·버그 수정은 운영 코드를 편집하기 전에 [테스트 워크플로우](../test-workflow/SKILL.md)를 시작한다. 동작을 보존하는 리팩터링은 기존 테스트로 계약을 먼저 확인한다. 후속 수정에서는 직전 조건 중 무엇이 바뀌었는지 확인한 다음 해당 경로를 다시 검증한다.
2. [실행 명령](../../../docs/testing.md#검증-실행)에서 변경에 맞는 검사를 실행한다. 화면 조작이 달라졌다면 사용자가 하는 동작을 실제 브라우저에서 수행한다. 관련된 입력으로 진입한 뒤 다른 대상으로 이동하거나 조작을 취소하고 원래 흐름을 이어갈 때도 기대한 상태인지 확인한다. 예컨대 최초 포커스는 정상인데 두 번째 항목에 이전 값이 남는다면 같은 순서로 수정 전후를 대조한다. 환경 때문에 실행이 막히면 실패 원인을 진단하고, 가능한 나머지 검증과 미확인 동작을 구분한다.

## 로컬 리뷰

원래 요청과 완료 조건에 비춰 최종 변경을 검토한다. staged·unstaged diff와 새 파일의 내용을 확인한다. 작은 변경은 메인 에이전트가 수정한 줄과 실행 결과를 짧게 대조하고 마친다. 범위가 넓거나 API·저장·화면 간 계약이 함께 바뀌거나 사용자가 독립 리뷰를 요청했으면, 시니어 개발자 역할의 독립적인 읽기 전용 Codex 리뷰어에게 **원래 요청, 관련 diff, 케이스별 테스트와 실제 검증 결과**를 전달한다. 리뷰어는 [테스트 판단 기준](../../../docs/testing.md)으로 반례를 찾고, 문제가 있으면 위치·재현 조건·사용자 영향을 구현자에게 돌려준다. 리뷰만 맡은 세션은 새 리뷰를 위임하지 않는다. 독립 리뷰어를 실행할 수 없으면 메인이 diff를 검토하고, 보고에 자체 검토 결과와 독립 리뷰가 미실행된 이유를 따로 적는다.

구현자는 발견 사항을 확인해 고치고 영향받은 검사를 다시 실행한다. 최종 보고에는 실제 수행한 작업 단위마다 단위명, 변경 내용, 검증 결과를 적는다. 미완료 단위나 확인하지 못한 항목이 있으면 이유를 함께 밝힌다.

작업 범위 판단, 검증 선택 등 워크플로우의 행동을 바꾸면 별도 작업 공간이나 새 Codex 세션에 평소의 개발 요청을 준다. 평가할 스킬이나 예상 결함을 미리 알려주지 않는다. 실행한 작업·검사·종료 지점을 요청과 비교하고, 어긋나면 지침을 고친 뒤 같은 요청으로 재시험한다. 평가용 변경은 실제 작업 트리에서 제외한다.
