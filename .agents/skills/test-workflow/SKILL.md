# 기능 변경과 버그 수정의 테스트 절차

## 구현 전

- 사용자의 요청, 완료 조건, 관련 [제품 결정과 PoC](../../../docs/product.md)에서 새 동작과 그대로 보장할 동작을 찾는다. 먼저 대화의 작업 메모에 케이스 목록만 적는다. 각 항목은 시작 상태, 행동, 기대 결과로 식별할 수 있어야 한다.
- [테스트 판단 기준](../../../docs/testing.md)에서 변경이 닿는 계층을 살핀다. 각 계층에서 생길 수 있는 사용자 피해와 그 결함을 잡을 가장 작은 테스트를 고른다. 단순 접근자나 라이브러리 자체 동작 등 테스트 생략 기준도 이 문서를 따른다.

## 기능 추가·동작 변경

1. 케이스 목록을 기준으로 구현한다. 추가 동작이 필요해지면 해당 코드를 쓰기 전에 그 동작의 기대 결과를 목록에 먼저 적는다.
2. 각 케이스에 대응하는 실행 가능한 테스트를 작성한다. 이미 같은 계약을 검증하는 테스트는 그 단언을 확인해 재사용한다. 구현하면서 새로 드러난 분기는 요구사항과 대조해 목록과 테스트 양쪽에 반영한다.
3. 목록과 실제 테스트 사례를 **1:1로 대조**한다. 파라미터화한 테스트라면 해당 입력 행까지 짚는다. 각 항목에서 어떤 단언이 그 잘못된 동작을 잡는지 확인한다.

## 버그 수정

1. 운영 코드를 편집하기 전에 사용자 증상을 재현하는 회귀 테스트를 준비한다. 기존 테스트로 재현되면 그 테스트를 사용한다.
2. 테스트를 실행하고 기대 결과와 실제 결과의 차이가 보고된 증상과 일치하는지 확인한다. 컴파일·환경 설정·외부 서비스 오류로 멈췄다면 원인을 해결하고 다시 실행한다. 수정 전 실패를 끝내 확인할 수 없으면 재현 미확인과 이유를 보고하고 그 항목을 열어 둔다.
3. 원인을 수정하고 같은 테스트를 다시 실행한다. 실패에서 통과로 바뀐 회귀 테스트를 저장소에 남긴다.

## 기존 테스트 보호와 완료

- 기대 결과는 제품 계약이 달라졌을 때 갱신하고, 무엇이 달라졌는지 설명한다. 구현이 기존 계약을 어기면 구현을 고치고 기존 단언을 유지한다. 변경 범위는 해당 동작과 이를 보호하는 테스트로 한정한다.
- 관련 테스트를 실행한 뒤 공유 코드와 연동 경계의 영향을 검토해 필요한 회귀 묶음까지 실행한다. 화면 조작이 바뀌면 실제 브라우저에서도 해당 입력과 표시 결과를 확인한다.
- 로컬 diff 리뷰에서 각 **케이스 → 테스트 이름 또는 파라미터 행 → 단언 → 실행 결과**를 대조한다. 빠진 케이스는 보완하고 다시 실행한다. 필수 테스트가 실패했거나 실행되지 않았으면 그 항목은 미완료로 보고한다. 수동 확인 결과와 버그의 수정 전후 실행 결과도 구분해서 전달한다.
